# FedMes 1.0.0 rev5 — устранение задержки отправки сообщений

## Найденные причины

До rev5 отправка одного обычного текста на Android и Desktop выполняла последовательно:

1. повторную регистрацию публичного ключа текущего устройства;
2. отдельную загрузку полного списка устройств чата;
3. локальное шифрование текста и RSA-OAEP-конвертов;
4. POST сообщения;
5. полную повторную загрузку чатов, presence, typing и до 100 сообщений;
6. повторную расшифровку до 100 сообщений RSA-ключом устройства.

Android foreground-служба одновременно получала событие о собственном сообщении и повторно обходила все чаты. На сервере все запросы к SQLite обслуживались одним соединением. Через Cloudflare это превращалось в несколько последовательных HTTPS round-trip и очередь запросов к базе.

## Исправления rev5

- Публичный ключ регистрируется один раз после входа, а не перед каждым сообщением.
- Список доверенных устройств чата кэшируется на 60 секунд и принудительно сбрасывается после подключения или отзыва устройства.
- Серверный ответ POST используется для немедленного добавления уже подтверждённого сообщения в интерфейс; повторная загрузка 100 сообщений больше не блокирует появление отправленного текста.
- Android-служба загружает только сообщения после последнего известного sequence и не перечитывает неизменившиеся чаты.
- Desktop действует по той же схеме и после POST обновляет локальную ленту сразу.
- SQLite WAL использует пул до четырёх соединений: чтения больше не стоят в одной очереди с каждым коротким запросом.
- Nginx больше не отправляет `Connection: upgrade` для обычных HTTP API-запросов.

## Безопасность

Кэш содержит только публичные ключи и идентификаторы активных устройств. Приватные ключи, ключи сообщений и открытый текст не кэшируются. При изменении списка устройств кэш сбрасывается; фоновый ремонт конвертов сохраняется.

## Применение на действующем VPS

После сборки нового Linux-комплекта замените `fedmes-server`, затем:

```bash
sudo systemctl restart fedmes
sudo systemctl status fedmes --no-pager
```

В существующем Nginx-блоке FedMes удалите:

```nginx
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

и используйте:

```nginx
proxy_set_header Connection "";
proxy_buffering off;
proxy_request_buffering off;
```

Затем:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## Проверка задержки

```bash
curl -sS -o /dev/null -w 'connect=%{time_connect}s tls=%{time_appconnect}s start=%{time_starttransfer}s total=%{time_total}s\n' \
  https://support-walrus.msk.ru/health/live
```

Проверка локального backend без Cloudflare:

```bash
curl -sS -o /dev/null -w 'start=%{time_starttransfer}s total=%{time_total}s\n' \
  http://127.0.0.1:8008/health/live
```

Если локальный запрос быстрый, а доменный медленный, задержка находится на пути клиент → Cloudflare → VPS. Если медленный и localhost, проверяйте CPU, диск и журнал сервиса:

```bash
systemctl status fedmes --no-pager
journalctl -u fedmes -n 100 --no-pager
iostat -xz 1 5
```
